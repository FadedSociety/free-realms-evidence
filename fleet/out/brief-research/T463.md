**Client evidence:**
- The 35/63 case is `case 0x3f` inside `0x0092f460` (`BaseClient::DispatchBasePlayerUpdate`, `client_sql` label). Its body starts near `0x009316ac`, close to the brief's `0x009316a0`.
- The case calls `0x008eafc0` (ctor: family 35, sub 63), then reader `0x00919c90`, which calls `0x008fc2d0`. `0x008fc2d0` reads an i32 count and then loops `count` times over `0x008cce90` and `0x008db2a0`. It stops early on reader error and has no client-side cap.
- `0x008db2a0` reads one u64 (two u32 words, error if fewer than 8 bytes remain), then one u32. Each entry is therefore 12 bytes: `{u64 guid, i32 anim}`.
- For each node, the case reads `node[0..1]` as the guid and `node[2]` as the anim. It looks the guid up with `FUN_00984960` (name and role unverified). If found, it calls `0x0096c780(anim, -1, 0, 0, 1, 0)`. Flag 0 makes it play now rather than queue (`0x0096c8b5` branch). Then it destroys the packet via `0x008eb030`.
- Client state is therefore transient: the packet plays each found entity once and keeps nothing.
- Wire header: `piece_052.rs:45-47` gives opcodes 35 and 8. Sanctuary's `PlayerUpdatePacketSetSynchronizedAnimations.cs:24-39` writes the base header, then `i32 count`, then `{u64 guid, i32 anim}` per entry. This matches the brief's layout.
- Locale: none needed for this brief.

**Reference implementations (Sanctuary snapshot `refs:Sanctuary-main-20261019`; the commit label 10f129e is unverified):**
- Synchronized step: `Sanctuary.Game/Helpers/BoomboxDancePlayback.cs:17-21` builds one shared clock per box. Each step length is the max of `DanceDurationsMs.Values` at that index, so it takes the max over all model keys in the row.
- Advance: `BoomboxDancePlayback.cs:24-37`. `_nextClipAt = now + duration - Math.Clamp(blend, 0, duration-1)`. The blend clamp is to `duration-1`, not a 1000 ms floor.
- Jingle Bell (878), `refs:Sanctuary-main-20261019/src/Resources/Consumables.json:3`: sequence [3531,3532,3533,3534], blend 600, durations for keys 1, 2, 60, 61. Step 3 is 10667 for models 1, 2 and 61 but 11000 for model 60. With the max, step 3 is 11000−600 = 10400 ms; for model 1 alone it is 10067.
- Model keys: `client Models.txt` rows 1 human_m, 2 fairy_m, 60 human_f, 61 fairy_f. The brief's model list is correct.
- Per-tick dancers: `BoomboxHelper.cs:179-198` takes players within `definition.Range` by 3D `Vector3.Distance` from a fixed spawn centre. The default range is 15 m (`BoomboxDefinition.cs:9`). Mounted players are excluded from dancing but kept in `activeDancers`.
- Owner rotation: `BoomboxDancePlayback.cs:50-75` takes max priority, keeps the current owner until its turn ends, then picks the least-served source. Ties are not broken by distance.
- Step send: `BoomboxHelper.cs:109-114` and `:383-402` send one packet to each target and each target's visible players, with no per-recipient filter.
- Joiners: newcomers get an idle 35/8 (`BoomboxHelper.cs:225-231`) and wait for the next step. No single-entry 35/63 is sent.
- Stop: `StopDancing` (`BoomboxHelper.cs:405-423`) sends one 35/8, Flags=1, animation 1.
- Mount pause: `BoomboxHelper.cs:363-381` (`PauseDance`, called from `PacketMountSpawnHandler.cs:83`) sends two 35/8 packets: one with Flags=1 and one with Unknown=1.
- Expiry: `BoomboxHelper.cs:152-176` stops every active dancer and then removes the box with a separate effect-tag removal.

**Risks and corrections:**
1. Predecessors T459 and T461 are unmerged (see status). The brief cites `src/boombox.rs` as if it exists. Until it lands, the codec and state are new in this slice.
2. Viewers need explicit self-entry. `visible_set` excludes the viewer (`players.rs:488`), so `knows_character(dancer, dancer)` is false. A dancer's own packet would drop its own entry unless it is added explicitly.
3. Gate 5's "nearer box wins at equal priority" is not Sanctuary's rule (R). Sanctuary rotates by least served.
4. Range is 3D from the spawn centre, default 15 m, not X/Z (R on X/Z).
5. The 1000 ms floor is not Sanctuary's behaviour. Sanctuary clamps the blend to `duration-1`. Keep the saturating math, but the floor is an invention.
6. Joiner single-entry 35/63 is not in Sanctuary (see above). Label it as a design choice or drop it.
7. Mount pause: Sanctuary sends two 35/8 packets, not one. Decide whether the second `Unknown=1` packet is needed. The native test in the brief would settle it.
8. The brief says "Sanctuary steps with a fixed clock"; Sanctuary uses `Environment.TickCount64`. Inject `now_ms` for tests.
9. Hub growth: `osfr-gateway.rs` is 4671 lines and `gameplay.rs` is a capped hub. The tick wiring must stay in `boombox_routing.rs`.
10. Lead-only areas touched: mounts (`set_mount` callers) and the registry's mount map. Do not change login or transport.
