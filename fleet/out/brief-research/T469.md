**Client evidence** (client_sql fn table; IDA broker not used):
- `00bd1700` reader: u16 at +4, i64 Time at +8/+0xC, i32 at +0x10 (ServerRate), bool at +0x14 (UseClientTime). Matches the brief, and the wire layout is 2+8+4+1 = 15 bytes.
- `00bd1830` apply: calls `00bd1700`, then vtable slot `+0x24` (slot 9, `SetFromUnixTime` per Game Rules note line 2140). Then `param_1[0x18]` (+0x60) = ServerRate. It sets the byte at +0x64 from UseClientTime, then copies +8 to +0x10. The toggle at `cStack_10 != param_1[0x19]` gives a copy, since the two values differ.
- `010bd270`: returns early if `*(char*)(this+0x64) != 0`. The local-time conversion `FUN_007026b0(..., 1)` uses `FUN_00d8c956` (local). So the client applies its own UTC offset, as the brief says.
- `010bd270` scaled path: if its flag argument is nonzero, it does `(secs % (0x15180 / scale)) * scale`. With scale 0 this divides by zero, so rate 0 must be refused.
- **Unverified:** the pseudocode drops the three stack arguments to the slot-9 call. Whether the flag passed is the reply's UseClientTime cannot be read from the decompile. Confirm with `ida_query.py decompile 00bd1830` when the broker is up.
- `010bd380` AdvanceClock: when unfrozen, it advances the day-second field by elapsed x scale and wraps at 0x15180 (86400). So the sky keeps moving at 8x between syncs. The 11 s cadence matters less than the brief implies.
- Sync cadence: `00bd16d0` returns `(this+8)-(this+0x10) < 11` (fresh). `00bd1b40` (PeriodicTimeReport) sends the client's own 52 request when that difference is `> 5`. Units are (R) seconds. The client asks; we reply.
- `007026b0` (localtime64): valid only when high dword < 7, or high dword = 7 and low < 0x93407000. That is max 32535215999. Out of range (or negative) it returns 0 and sets the local date to 1970, which is a sky jump.
- `010bd190` ctor: sets scale `+0x60` = 8 (`param_1[0x18]=8`) and the byte at +0x64 = 0.

**Risks and corrections:**
1. **False gate.** The brief says `Time <= 32535215999` for every now up to 4102444800 (2100-01-01) "at rate 16". That is wrong. At rate 16 and now = 4102444800, Time = 16 x 2881083130 = 46,097,330,080, which exceeds the cap. At rate 16 the cap is reached at now = 3254812669 (about 2073). At rate 8, now = 4102444800 gives 23,048,665,040, which is inside the cap. Fix the test to rate 8, or have the lead decide a clamp (a clamp freezes the sky at the cap, and out-of-range shows 1970).
2. **Hub growth.** `gateway.rs` has 10 lines of slack. The arm is currently 16 lines, so a net-negative change is feasible. If `Gameplay::game_clock()` is added in `gameplay.rs` (also a capped hub), keep it to a few lines or have the gateway read the file.
3. **Clock argument.** Add an explicit `now_unix` parameter to the helper. Do not use `handle_at`'s `now_ms`.
4. **Lead-only:** none of login, accounts, sessions, transport, roles or `launcher/` is touched by this brief.
5. **Brief claim to keep:** "a freshly-synced sky" and `rate` 8 are correct. The first reply sets the sky from `Time = now`, which is the old wall-clock behaviour.
