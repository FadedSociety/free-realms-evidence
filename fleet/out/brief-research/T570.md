**Client evidence** (`client fn`, read-only):

- Body, in reader order (L = the 36/4 object base; wire bytes, little-endian):
  1. `u64` Guid at L+0x10 (`00a31f30`, two dwords).
  2. Targets: `i32` count at L+0x18, then elements. `00a2fab0` rejects a negative count. It also rejects a count larger than the remaining bytes. The compare is `(int)end - cursor`, a byte difference, so the bound is bytes, not elements. Each element is read by vtable slot +4 (Target reader, not recovered).
  3. `i32` L+0x28, `i32` L+0x2c, `i32` L+0x30, `i32` L+0x38, `i32` L+0x34.
  4. `u8` bool L+0x3c, `u8` bool L+0x3d (nonzero = true).
  5. `i32` L+0x40, `i32` L+0x44, `i32` L+0x48.
  6. `f32[4]` L+0x50 (`008e2410`).
  7. `f32` L+0x60 and `f32` L+0x64. Each sets a NaN flag at reader +0x11 and still stores the value.
  8. `i32` L+0x68.
  9. ActionBar: two `i32` (Id, Slot) via `008dadd0`. The destination base is not in the tail shown; the gap fits L+0x6c..0x73 (R).
  10. `i32` L+0x74.
  11. `u64` TargetGuid at L+0x78.
  12. `u8` bool L+0x80.
  13. ProjectileParameters via `008e8910` (end of `00a31f30`). Its base is not visible (R).
- ProjectileParameters, in reader order (P = its base; from `008e8910`, read in full):
  1. `i32` P+0x10; `i32` P+0x14; `f32` P+0x18 (NaN flag); `f32` P+0x1c (NaN flag); `i32` P+0x28; `i32` P+0x2c.

  3. String: `i32` length (must be >= 0 and fit), then raw bytes.
  4. Target via slot +4 on the pointer at P+0x30, then on P+0x38.
  5. `f32[4]` P+0x70; `i32` P+0x80 (NaN flag); `u8` bool P+0x40; `f32` P+0x20 (NaN); `f32` P+0x24 (NaN).

  7. Four values via `008d53b0` at P+0xc0, c4, c8, cc. Their type is unverified.
  8. String via `008e2470` at P+0x94.

**Risks and corrections:**
- The brief says the "ability and effect ids" are in 36/4. Sanctuary has no ability-id field in 36/4 (see above). U10 is the effect id (R). The ability id is in 36/3.
- The target-count bound is a byte bound, not a per-element bound. A stricter cap is your choice (R).
- "Reader-faithful" conflicts with "reject trailing bytes". The client reader does not check for trailing bytes in the parts I read (unverified for `00a33760`). Our `Reader` in `piece_035.rs` already enforces exact length, so that policy is ours, not the client's.
- NaN floats: the client accepts them and sets flag +0x11. Whether the caller rejects on that flag is unverified.
- Do not flip `ProjectilePayload::launch_and_land()`. That breaks `tests/piece_035.rs:434-436`. Put the codec in a separate type, or change the test deliberately.
- Hub growth: `piece_035.rs` (597 lines) is not a capped hub. Lead-only areas are not touched.
- The Target element reader is a gap. Either encode Target as an opaque sub-frame or recover it first; T571 (snowball piles) depends on this.

**Suggested tests:**
1. Byte test: encode a fixed 36/4 frame in reader order (header, Guid, Targets, the fields above) and assert exact bytes. This fails if you swap any two fields.
2. Decode the same bytes and assert every field round-trips.
3. Truncate the frame by one byte at each boundary and assert a reject. Also append one trailing byte and assert a reject.
4. Count bound: a target count above the remaining bytes, and a negative count, are both rejected.
