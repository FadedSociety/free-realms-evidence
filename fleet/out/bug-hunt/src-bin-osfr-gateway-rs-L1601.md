- **[low] `osfr-gateway.rs:1928-1938` with `1938-1951` - the character save is inside the "precommit" closure, so a later social/chat/guild save failure on a transfer returns `Ok(false)` with the disk already written.**
  - **Failure scenario:** a zone-change bundle reaches `prepare_membership` successfully. `outcome.state_changed` is true and `transfer` is true, so `1935` runs `save(&self.state_path, &staged_gateway.snapshot())` and the new zone and pose reach disk. `persist_social_changes` (`1938`, which writes profile files) or `staged_world.guilds.save_changed()?` (`1942`, `t006_guilds.rs:53-57`) then fails with an I/O error. `Err(_) if transfer => return Ok(false)` (`1951`) swallows the error silently. `self.gateway`, `world` and `membership` stay on the old state, and no zone-change reply is sent. On disk the character sits in the new zone; in memory the session is still in the old one. Social profile files written at `1938` are likewise ahead of the in-memory `world`.
  - **Reach:** a remote client sends a zone-transfer bundle (`dispatch_message_inner` → `commit_outcome`, `1673`). Nothing the client sends causes this; it needs the post-save writes to fail (disk full, permissions, or I/O error). Upstream checks do not cover it: `prepare_membership` (`world.rs:990-1046`) runs before the save, so input-driven refusals never reach the save. The comment at `1949-1950` ("A precommit transfer refusal keeps the live session/location/members") is therefore false for failures after `1935`.
  - **Fix:** move the character save (`1928-1937`) out of the closure, after `persist_social_changes`, `chat_settings.save_changed` and `guilds.save_changed` have all succeeded, so every fallible write precedes the single commit point. Or log the swallowed error at `1951` and stop treating post-save failures as refusals.

Member 3 is never healed, and the kill is already claimed (`world.rs:875-886`), so it cannot be retried. The picker's own commit at `2038-2039` has already landed.
  - **Reach:** the picker's shared-field action (`commit_outcome` → `outcome.group_heal`, `1838`) triggers `heal_group` after commit. Only an I/O failure on a member's save triggers the early return; the client controls the kill, not the failure.
  - **Fix:** collect the failures and continue healing the remaining members, or save all staged member gateways before any `session.gateway` replacement, so a failure leaves no member partly updated.
