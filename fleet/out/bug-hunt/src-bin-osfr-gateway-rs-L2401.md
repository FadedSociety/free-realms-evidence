  - Failure scenario: picker P has big-heart kill K, group members M1 and M2 are in P's zone and instance, and M1's send queue is full (a lagging client). Step by step: `claim_group_heal` (2399) records K. For M1, `receive_group_heal` at 2422 succeeds, `save` and `session.gateway = staged` run at 2424-2425, then `queue_shared_message(...)?` at 2428 returns `SendError::QueueFull` (`soe_send.rs:157`). The `?` returns Err from `heal_group`, so M2 is never healed or saved. The claim is already recorded, so there is no retry. M1 now has healed HP on the server that the client was never told about. P's dispatch also gets Err after P's own commit (2038-2040).
  - Reach: `process` → `commit_outcome` (2038-2040) → `heal_group` (2387) → 2428. Nothing upstream checks the queue state. `soe_send.rs:137-157` returns `QueueFull` as a normal condition. The sibling code at 3147-3149 and 3192-3194 deliberately refuses only the affected recipient, so this is inconsistent.
  - Fix: at 2428, replace the `?` with `if let Err(error) = session.queue_shared_message(&wrap_application(&reply)) { event(json!({"event":"group_heal_refused","character":session.character_guid,"reason":error.to_string()})); break; }`. This keeps the other members going and matches the field path.

- **[medium] prototype/osfr-tools/src/bin/osfr-gateway.rs:3134-3140 - `tick_shared_instance` writes several character saves in a loop, and a failure partway leaves a reward on disk that the live field and gateways never adopt.**
