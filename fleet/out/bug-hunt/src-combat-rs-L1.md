I read combat.rs 1-408 in full and traced the callers. Nothing in the window itself panics, overflows, or mutates before an error return on client bytes. Packet lengths are checked before every slice, `(26,8)` checks `len == 13` before `inner[12]`, the ability path checks `len >= 16` before reading `target`, `checked_sub` handles a backwards clock, `defeats` is guarded against `u64::MAX`, and `spawn` writes its fixed offsets before the variable-length splices. The one real finding is a trust issue whose range check lives in this file.

- **[medium] combat.rs:232 (also :274-275 and :193, :296, :301-303) - the range gate trusts a client-reported player position, so the "within 8 units" rule can be bypassed by sending a pose.**
  - **Failure scenario:** a player sends a movement/pose packet placing their character at the training enemy's content position (or the NPC's position). The server accepts it, so `attack()` passes the `near()` check and hits the enemy from anywhere on the map. Repeated `respawn()` from the NPC's position, also reachable by teleport, allows unlimited farming of the training enemy. Each defeat calls `quests.enemy_defeated` (gameplay.rs:5387-5389), so quest progress and its rewards can be accumulated faster than intended. The 4 s cooldown (`cooldown_ms`) still applies, so this is a bypass of range, not of rate.
  - **Reach:** movement packet → `players.rs:412` (`changed.position = position`, set from client input) → `players.rs:654-659` `validate_pose` only checks `is_finite()`, with no speed or distance check against the previous position, and it ignores the `max_movement_speed` the client sends in `PlayerPresentation` → `gameplay.rs:2333` `self.handle(inner, character.guid, character.position, now_ms)` → `combat.rs:166-171` `handle(inner, position, …)` → `combat.rs:221-222` / `:201` → `attack(position, …)` → `combat.rs:232`. Nothing upstream in combat.rs or gameplay.rs compares `position` with server-held state before the range check.
  - **Fix:** this is a movement-validation gap rather than a combat.rs bug. The minimal fix in this window is none. The real fix is to reject or clamp pose jumps in `players.rs::update_pose_with_state` (for example, a maximum displacement per elapsed `now_ms` derived from `max_movement_speed`) before the position is stored. If a per-file fix is required, `near()` cannot be made authoritative without a server-side position, so it must be fixed upstream.
  - **Confidence note:** this is systemic (quests, NPC interaction, and enemies all trust the same position), so a refuter may reasonably classify it as a known design limitation of the prototype rather than a combat.rs defect. I am reporting it because the range rule in this file is not enforced against anything the server controls.
