# prototype/osfr-tools/src/gameplay/placement_watch.rs lines 1-397 of 397

Reviewed `placement_watch.rs` lines 1-397 and the callers it depends on (`gameplay.rs` 3736-3927, `world.rs` 425-456, 580-600, 703-705). I found no defect a remote player can trigger. The placement file is written only by the admin-only `realm place` / `realm unplace`, and every client-reachable input is checked before it reaches this file. The poll, retry, and `Rejected`/`Absent` stamp logic is consistent with its doc comments. `replace_placements` is only ever called on a clone in the watch path, so a failed apply leaves the live view intact. One narrow logic defect remains:

- **[low] `placement_watch.rs:125` - `apply_own_placement_write` re-stats the file after the write and apply, so it can record a stamp that covers another writer's change that this session never applied.**
  - **Failure scenario:** Admin A runs `realm place` at time T and `save_placements` lands mtime M_A. Before A's `observe` at line 125 runs, admin B's `save_placements` lands mtime M_B. A's `replace_placements` and `update` build packets from A's own `records`, which do not contain B's row. Line 125 then calls `observe`, which stats the file now on disk and stores `Stamp::Modified(M_B)`. A's next poll sees the stamp matches and returns `None`, so B's row never reaches A's view until some later write changes the file. The window is the packet-build time between save and observe, so it is milliseconds wide and needs two near-simultaneous admin writes.
  - **Reach:** `gameplay.rs:3881` (`place_npc`) and `gameplay.rs:3925` (`unplace_npc`) call `save_placements` (3876, 3920), then `apply_own_placement_write` (`placement_watch.rs:113-127`), which calls `observe` after the apply. Nothing upstream re-reads the file under the same stamp, and `save_placements` has no lock, so the stat is not tied to the saved bytes. The doc comment on `observe` ("Record the file a session just loaded or wrote") describes the saved file, but the code records whatever is on disk at call time.
  - **Fix:** Capture the mtime right after the save (have `save_placements` return it, or stat immediately after `replace_bytes`) and pass that value to the watch instead of re-stat'ing after apply. Alternatively, call `observe` before `replace_placements`, so that a change landing during the apply is still seen as newer on the next poll.
