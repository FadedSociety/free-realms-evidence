**[medium] `prototype/osfr-tools/src/gateway.rs:1718` - a later successful child in the same bundle overwrites an earlier child's `shared_field` action with `None`, so that action is silently dropped.**

- **Failure scenario:** A client sends a `[0, 25]` bundle. Child 1 is a shared-field action (for example an ability or attack in a shared encounter field). `gameplay.rs:2291-2296` returns `Outcome { shared_field: Some(action), ..Default::default() }` with no state change. Child 2 is an ordinary in-world application (e.g. a chat line) that `handle_in_world` accepts. At line 1718, `outcome.shared_field = result.shared_field;` runs with `None` and clears child 1's action. The staged game from child 2 is still committed, but the field action never reaches `osfr-gateway.rs:1700`, so it is never applied to the field.
- **Reach:** `handle_at` (gateway.rs:1414) sets `combined` for `[0, 25]` bundles and iterates every child. Child 1 passes the `known_no_reply` check at 1704-1716 because `shared_field.is_some()`. Child 2 reaches line 1718 when its handler returns `Ok`. Nothing upstream prevents this.
- **Inconsistency:** The same block already states the intended rule at lines 1719-1721 (T199): a later non-broadcast child must not clear an earlier notice. That rule is applied only to `broadcast` (line 1721, `result.broadcast.or(outcome.broadcast.take())`). `Outcome::absorb` in `gameplay.rs:311` uses `shared_field.or(self.shared_field.take())`, which keeps the earlier action. Line 1718 is the one place that breaks the pattern.
- **Fix:** Replace line 1718 with `outcome.shared_field = result.shared_field.or(outcome.shared_field.take());`, matching `absorb` and the broadcast rule. If two shared actions in one bundle must both run, `shared_field` needs to become a list, but the single-slot `or` is the smallest fix.
- **Severity note:** The effect is a client-triggered loss of its own field action, with no coin or item gain shown. That is why this is medium, not high.
