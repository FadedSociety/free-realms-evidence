Two low-severity findings:

- **[low] prototype/osfr-tools/src/guilds.rs:1461-1462 (with insert at 398-405 and reclaim at 518-521) - the invite target is taken from the client's `second_guid` with no check that the GUID is a real character, and pending rows for those GUIDs are kept for two invite windows.**
  - Failure scenario: a leader or officer sends many 129/3 invites, each with a fresh `second_guid` that matches no character. `store.invite` inserts one `PendingInvite` per GUID (398-405). The only reclaim is `expire_invites`, which drops a row only after `now - window >= expires_at` (518-521), so each row lives about 240 s with the default 120 s window. Memory grows with the packet rate times 240 s, with no count cap. The rows are runtime-only, so nothing is persisted.
  - Reach: a client packet, `GuildRequest::Invite` decoded at guilds.rs:1972-1976, goes to `handle_decoded` (1450-1493). The gateway passes the body unchanged (`t006_guilds.rs:173-174`). The only checks are `guild_guid_for(actor)` and the rank check in `store.invite`. The non-zero `second_guid` branch at 1461-1462 bypasses name resolution, so nothing checks existence. The attacker needs officer or leader rank in a guild, which requires one eligible character to create a guild.
  - Fix: when `second_guid != 0`, require that the GUID is a known character identity (the gateway's `identities` map) before calling `store.invite`, or cap `pending_invites` and drop the oldest rows when it is full.

- **[low] prototype/osfr-tools/src/guilds.rs:887-889 (with no count limit at 270-329) - the guild store has a hard 1 MiB save cap, but nothing caps the number of guilds, so persistence can stop permanently.**
  - Failure scenario: many characters each create a one-member guild (`create_guild` checks only the caller's own membership, eligibility and the name, never `guilds.len()`).   - Reach: `handle_decoded` Create (1407-1430) → `store.create_guild` (270-329), with no upstream cap. The gateway flush propagates the error via `?`.
  - Fix: reject `create_guild` when `self.guilds.len()` reaches a documented maximum, sized so the serialized store stays under `MAX_STORE_BYTES`. Alternatively, raise the cap or move to per-guild files.
