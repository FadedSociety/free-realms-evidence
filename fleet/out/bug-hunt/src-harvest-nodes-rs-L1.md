- **[medium] prototype/osfr-tools/src/harvest_nodes.rs:371-384 - `payout_fits` sizes the bag check from `goal.quota`, but the real win pays from `collected`, which can exceed quota, so the start gate can admit a run whose settlement then cannot be stored.**
  - Failure scenario: a player starts a Chef or Miner run with a bag that has exactly enough room for the quota-based payout. During the run, a chain or gravity fall adds several goal tiles in one move (`mining.rs:1588` and `mining.rs:1638` add one tile per collected tile, with no cap at quota). The goal completes with `collected` above `quota`. `settle_after_collect` (`mining.rs:1664-1676`) then sets `LevelComplete`. On `OnNextLevelMsg`, `reward_transaction` (`mining.rs:1705`) computes `collected / per_reward`, which is larger than the gate's `quota / per_reward`. `grant_bundle` fails for lack of space, `apply_type8` returns an error (`crafting.rs:443-487`), and the staged clone is discarded. The run stays in `LevelComplete`, and each retry fails the same way until the bag has room. The doc comment on `payout_fits` (lines 369-370) says a stranded win is exactly what this gate is meant to prevent.
  - Reach: client `26/8` → `gameplay.rs:2516` `admit` → `gameplay.rs:2528` `payout_fits`. The gate is only checked once, at run start, so the later overshoot is not covered. The client controls how many tiles one move collects.
  - Fix: in `payout_fits`, bound each goal's clusters by the most that can be collected, not by `quota`. For example, use `goal.quota.saturating_add(max_chain_size)` (or a cap on tiles per board) before dividing by `per_reward`. Alternatively, cap `run.collected[goal_index]` at `quota` when it is incremented in `mining.rs:1588` and `mining.rs:1638`.

- **[low] prototype/osfr-tools/src/harvest_nodes.rs:348 - the guid "game kind" tag is OR'd into bits that `NODE_GUID_BASE` already sets, so the kind never encodes what line 23 documents.**
  - Failure scenario: `NODE_GUID_BASE` is `0x4e4f_4445_0000_0000` ("NODE"). Bit 32 is already set, so `tag << 32` with tag 1 changes nothing, and tag 2 turns the final byte from `E` (0x45) into `G` (0x47). Harvest guids are therefore `…45xxxxxxxx` and mining guids `…47xxxxxxxx`. The two spaces stay disjoint, so no collision occurs. Nothing else decodes the tag bits (`is_node` at `harvest_nodes.rs:248` is a plain map lookup), so there is no observable effect today.
  - Reach: `load` at `harvest_nodes.rs:222-241` calls `add_sites`, and every guid comes from line 348. Only the map key is affected.
  - Fix: use a separate field for the kind, e.g. `NODE_GUID_BASE | tag << 24 | u64::from(spawn.id)` with the kind in a bit range that does not overlap "NODE", or move the tag into a clean 16-bit field below the tag bytes. Also update the doc comment.
