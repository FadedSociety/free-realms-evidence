Every slice in `patch_self`, `Reader`, `rows` and `resolve` is bounds-checked before use. The `patch_self` layout matches the Sanctuary `ClientPcData.Serialize` order (`refs/FreeRealms-Legacy/.../ClientPcData.cs:452-469`).

**[low] prototype/osfr-tools/src/identity.rs:305-308 and 338-339 - the client's clothing tint ids and eye/hair colour ids are accepted as any non-negative `i32`, with no check against a tint or colour table.**
- **Failure scenario:** a native creation submits `c[12]` (or `c[18]`/`c[19]`) = 2000000000. `resolve` accepts it because the only test is `< 0`. `validate` (line 136) also only tests `< 0`. `apply_identity` (`gameplay.rs:5255-5257`) then calls `grant_with_tint(0, definition, 1, 2000000000)`, which stores a starter clothing instance with that tint. The same value is persisted and sent in the character list and self packet as eye/hair tint.
- **Reach:** client packet opcode 5 → `login.rs:345` `NativeCreation::decode` → `account.rs:149` `resources.resolve` → `identity.rs:308` → `gameplay.rs:5257` grant. Nothing upstream bounds the tint. `Resources::load` loads no tint table, so the server cannot check it. The design note `notes/Build Guides/Gameplay/Character and Customization.md:293` asks the server to accept only ids that resolve through the option and mapping rows.
- **Caveat:** this is cosmetic. The grant is one clothing item per slot per creation, with no coin or quantity gain. I could not show a crash on the server, so this is a weak finding and may be refuted.
- **Fix:** load the tint/colour rows from `CharacterCreateItemMappings` (type 2/3) and require `c[12..17]`, `c[18]` and `c[19]` to be members of that set.

**Checked and dropped (not defects):** the `patch_self` offsets (`identity.rs:355-400`) are all guarded by `len >= 33` and `get`. `names_start` uses `checked_add`. `Reader::take` uses `checked_add` and `get`. The `rows` 32 MiB check runs after `fs::read`, but this is a local resource file, not client input. `save` creates the parent directory before the size check; this is harmless.

**Out-of-window lead, not counted (`gameplay.rs:5255-5263`):** `apply_identity` grants each attachment with a separate committed `grant_with_tint` and only sets `identity_fingerprint` after the loop. A failure on the second or later attachment would leave the earlier grants in inventory and return an error with no fingerprint, so a retry would grant them again. I did not trace whether that failure is reachable.
