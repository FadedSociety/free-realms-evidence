One logic defect:

- **[medium] `src/inventory.rs:701-704` - `equip_owned_definition` picks the first owned instance of a definition regardless of tint, so it can equip a different instance from the one the caller just granted.**
  - **Failure scenario:** The bag already holds item A (definition D, tint 5, id 10, e.g. from an earlier grant or store purchase). A job outfit switch with `reuse_owned == false` runs `grant(0, D, 1)` (tint 0). `grant_with_tint` (inventory.rs:997-1000) matches on `tint`, so it creates a new tint-0 item B (id 11). `equip_owned_definition(D, job)` then runs `.find(|i| i.definition_id == definition_id)`, which returns A because it comes first in `state.items`. The equipment slot gets A (tint 5), and the freshly granted tint-0 item B stays unequipped. The client shows the wrong tint. The same happens in the identity path, where `grant_with_tint(0, def, 1, tint_id)` is followed by `equip_owned_definition(def, 1)` and equips the first instance even when its tint differs from `tint_id`.
  - **Reach:** `gameplay/jobs.rs:47`, `gameplay/jobs.rs:56` and `gameplay/jobs.rs:105` (job outfit application, where definitions come from job tables and the bag may hold tinted copies). `gameplay.rs:5256-5259` (`apply_identity`, which runs once per character). Nothing upstream filters on tint. `validate_state` does not forbid duplicate definitions, so several instances can coexist.
  - **Fix:** Have `equip_owned_definition` take the tint (or the target instance id) and match `item.definition_id == definition_id && item.tint == tint`. For the existing callers that want the default look, match `tint == 0` or pass the id returned by the grant. This is cosmetic only: no items or coins are gained, and `equip` still enforces slot, class and profile.

Considered and dropped: the eligibility bypass in `equip_owned_definition` (it passes `None` to `equip`, skipping `ineligible`). The identity path is limited to creator-resolved items (`identity.rs:277-300`, `account.rs:149`), so it is not a remote item grant. Also dropped: the `Requirement::from_wire` fail-open for short rows, which is documented and concerns operator-supplied content only.
