- **[medium] prototype/osfr-tools/src/kart_service.rs:1787-1804 - the boost request (`33/22`) mints a queued boost with no server-side rate limit. The doc comment's claim that the three-slot queue "is the pacing bound" does not hold, because the use path consumes the entry immediately.**
  - **Failure scenario:** during a live race, a client sends `33/22` (owned guid only) and gets a queued type-5 entry (`queued_items.push`, line 1804). It then sends `33/19` (USE_ITEM), which pops the head entry (line 1860) and returns item 5 in `33/19`'s response (1870-1873). Each request/use cycle leaves the queue empty again, so the cap of 3 never binds. The sender can repeat this as fast as it can send frames, and the server only checks phase, ownership and `race_elapsed` (1787-1790). The `last_boost_epoch` written at line 1803 is never checked against the clock, so it does not limit anything either.
  - **Reach:** `handle_inner` (1765) with subtype 22 (`BOOST_REQUEST_SUBTYPE`), reached from the `33/*` kart frame dispatcher. Only the guid is validated (`owned_id` 1776, `own_guid` 1777), and no interval, count or ownership of an earned award is checked. The code comment says this is deliberate: the native refill is client-side and "No fixed interval gates this request." The code is still a trust-the-client gap, since a modified client gets unlimited boosts. It is not a crash, a coin gain or a save corruption.
  - **Fix:** either bind the request to a server-side budget (for example, a minimum `elapsed` gap between accepted boost requests, using the already-saved `last_boost_epoch`, or a per-race cap of boost grants), or correct the comment so it no longer calls the queue a pacing bound. Confirm the intended design with the owner before changing behaviour, since the comment cites native-client evidence.
