- **[medium] prototype/osfr-tools/src/login.rs:351-359 (also 464-468) - Each session caches its own copy of the account store and saves a whole-store clone of that stale copy, so concurrent sessions lose each other's characters.**
  - Failure scenario: Two loopback clients (sessions A and B) both log in as the local session name. Both load the store at login (`authenticate_account`, lines 207-259), so both have `next_character_guid = 1`. A creates "Alpha Beta" as guid 1 and saves to disk. B then creates "Gamma Delta": `staged = store.clone()` is B's stale copy, so `insert_character` also assigns guid 1, and `staged.save` overwrites the disk file. Alpha vanishes from disk. B's `character_name_taken` check also never saw Alpha's name, so a duplicate name can get through. Delete (lines 464-468) has the same stale-write problem.
  - Reach: `bin/osfr-login.rs:854` creates a `Session` per peer, with its own `LoginService` from `options.service()` (line 482). Up to 32 sessions run concurrently (`sessions.len() < 32`, line 852). Nothing in the unauthenticated path reloads or locks the store. The authenticated path avoids this by reloading per request under a lock (`bin/osfr-login.rs:769-774`, comment says so explicitly). Unauthenticated mode is loopback-only (`bin/osfr-login.rs:117`), so the attacker must be a local process. Hence medium, not high.
  - Fix: in the create (line 351) and delete (line 464) branches, reload the store from `self.config.account_store_file` (via `AccountStore::load`) and re-run the account/ownership checks on that fresh copy before cloning and saving. Alternatively, share one store handle across sessions.

- **[low] prototype/osfr-tools/src/login.rs:359-364 - The account store is saved before the identity file, and an identity write failure returns an error with the character already persisted on disk.**
  - Failure scenario: For account 1, guid 1, `staged.save` (line 359) succeeds and writes a character to the account store. `identity::save` (line 362) then fails (disk full, permissions). The `?` returns early, so the client gets no create reply, the session is dropped (`bin/osfr-login.rs:876-879`), and `self.account_store` keeps the old state. The next login loads the store with the new character, though the client was told creation failed. The legacy identity file is also left stale.
  - Reach: client opcode 5 → `handle` (line 341) → `identity::save` (line 362). It needs a local I/O failure, which is not attacker-controlled.
  - Fix: write the identity file first, or on identity failure roll back the store file, or make the identity write non-fatal and log it, so the reply and disk agree.

- **[low] prototype/osfr-tools/src/login.rs:527-531 - The migration temp file, which holds the legacy character state, is leaked when `write_all` or `sync_all` fails.**
  - Failure scenario: `create_new` succeeds, then `write_all` (line 531) or `sync_all` (line 532) returns an error. The `?` exits before `fs::remove_file` (line 542), so a `/tmp/osfr-login-migration-*.json` file with the save contents stays behind.
  - Reach: `authenticate_account` → `migrate_legacy_account_store` (line 224). It needs a local write failure.
  - Fix: wrap the write and sync in a closure, and on error call `let _ = fs::remove_file(&projected_path)` before returning.
