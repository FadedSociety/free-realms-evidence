# prototype/osfr-tools/src/movement.rs lines 1-384 of 384

**[medium] prototype/osfr-tools/src/movement.rs:280 - The per-report `MIN_INTERVAL` floor (plus the flat `VERTICAL_GRACE` at 290-291) grants a fresh 50 ms of movement allowance on every report, so a client that sends position reports faster than 20/s, or several in the same millisecond, is never held to the speed envelope.**

- **Failure scenario:** The server has accepted a report at t=1000 ms, so `last_movement_ms = Some(1000)`. The client sends 100 opcode-125 position reports all stamped in the same millisecond (or 1 ms apart). For each one, the gateway computes `elapsed = now_ms - last = 0`, and `validate` floors it to `dt = 0.05`. With the gateway's base speed of 10 (gateway.rs:1528), `soft_horizontal = 10 × 0.05 × 40 = 20` units and `hard_horizontal = 40` units. Each report moves 20 units horizontally and passes as `Accept` (or as `Clamp` at 20). Since `last_movement_ms` is set to `now_ms` on every accept (gateway.rs:1581), the next report again sees elapsed 0. Result: 100 reports in roughly 1 ms move the player 2000 units. Sustained packet rate R gives about 20·R units/s, which is 50× the intended 400 u/s at 20 packets/s. Vertically, `VERTICAL_GRACE` (20 units per call, unconditional) gives the same unbounded climb with no time element.
- **Reach:** Client opcode 125 → gateway `Event::Position(update, None)` (gateway.rs:628) → `handle_at` (gateway.rs:1409, `now_ms` from the caller) → `Event::Position` arm at gateway.rs:1499-1516, which computes `elapsed` with no minimum spacing → `movement::validate` (gateway.rs:1522). I found no per-connection rate limit on this path in the code I read (`rate_limit`/`RateLimit` have no hits under `prototype/osfr-tools/src`). The only check upstream is the position/direction finiteness and bounds checks at movement.rs:213-229, which do not stop a speed-per-packet bypass.
- **Why the window's own comments don't cover this:** the doc at movement.rs:12 says the floor exists to stop "tiny/quantized receive intervals from producing a zero allowance." It does that, but it converts a time-based cap into a per-packet cap. Nothing amortises the allowance against elapsed time that has already been granted. The `SOFT_SPEED_MULTIPLIER` doc (movement.rs:14-16) describes an envelope for real movement at roughly 382 u/s, not a per-packet budget.
- **Fix:** Don't accept reports that arrive faster than the floor. Add a `Reason` variant (for example `ReportTooSoon`), and before the speed checks, add `if elapsed < MIN_INTERVAL { return ValidationResult { decision: Decision::Ignore, state: *previous, reason: ReportTooSoon, expected_discontinuity } }`. The gateway's `Ignore` arm (gateway.rs:1536-1545) does not update `last_movement_ms`, so the next report's elapsed still measures time since the last accepted pose and the allowance amortises correctly. Existing tests use 50 ms intervals (tests/movement.rs:96-218), so they are not affected.
