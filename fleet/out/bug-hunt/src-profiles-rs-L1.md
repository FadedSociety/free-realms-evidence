One finding, latent and low severity. Nothing in the window is reachable from a client packet with a bad value.

- **[low] prototype/osfr-tools/src/profiles.rs:422-424 - `select()` commits `state.active` via `activate(id)?` and then calls `activation(id, inventory)?`; if the second step fails, the function returns `Err` with `active` already changed, and nothing restores it.**
  - **Failure scenario:** `select(43, inv)` is called with profile 43 unlocked. `activate(43)` sets `self.state.active = 43`. `activation()` then fails inside `inventory.profile_attachments(43)?` (inventory.rs:648-674), for example because an equipment row for profile 43 names an item id that is missing from `state.items` (inventory.rs:662) or a definition is missing (inventory.rs:667). The caller gets `Err`, but the profile is now active as job 43 with no 38/21 activation sent, so client and server disagree.
  - **Reach:** The only production call with a variable-free id is gameplay.rs:5012 (`.select(43, &self.inventory)?`, inside `enter_opening_cave`, reached from the opening-cave entry). The `?` there propagates without rollback. The other production callers (s15_npc_transactions.rs:263 with `MINER_PROFILE_ID`) are test code. A client cannot choose the id, and `decode` (profiles.rs:434) cannot fail for content validated at load (profiles.rs:154-168). The only failure is server-side inventory inconsistency, so this is not remotely triggerable with current content. The sibling job-switch path (gameplay/jobs.rs:159-182) avoids the problem by working on a `self.clone()` staged copy and committing only on success.
  - **Fix:** Make `select` atomic: compute the activation on a candidate without mutating, then assign. For example, `let mut next = self.clone(); next.activate(id)?; let packet = next.activation(id, inventory)?; *self = next; Ok(packet)`, or check `unlocked.contains(&id)` and call `activation(id, inventory)?` before `self.state.active = id`.
