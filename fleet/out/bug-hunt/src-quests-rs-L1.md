- **[medium] prototype/osfr-tools/src/quests.rs:289-328 - `load` rejects a save whose objective counts all equal `required` but whose quest is not completed, which contradicts the `(R)` comment at line 289 ("Objective edits must not prevent login").**
  - Failure scenario: a quest has one goal saved at 3/5 with `accepted: true, completed: false`. A content edit lowers `required` to 3. Repair at 296-297 does not fire (3 is not `> 3`, and `completed` is false). Validation at 321-325 computes `all(count == required) == true` while `completed == false`, so it returns `Err("saved quest progress is inconsistent")`. The engine fails to load and the character's quest state (and login through `gameplay.rs:1154`) fails.
  - Reach: `QuestEngine::load` is called from `gameplay.rs:1154` with the saved `QuestState`. This is a save+content path, not a remote packet. Remote play cannot produce count==required with completed==false, because `enemy_defeated` (463-504) always sets `completed` when all goals are met.
  - Fix: in the repair predicate at 296, also reset when `progress.completed != all_goals_met`, or derive `completed` from the counts at load instead of rejecting.

- **[low] prototype/osfr-tools/src/quests.rs:359-363 and 510-511 - `reset_session` zeroes `next_trial_ms`, so the checkpoint-activity cooldown is bypassed by reconnecting.**
  - Failure scenario: a player completes the activity at time T (`next_trial_ms = T + cooldown_ms`, line 593-603). They reconnect (the gateway keeps the same `Gameplay` object and calls `game.reset_session()`, gateway.rs:1382-1396 to gameplay.rs:1507-1511). `next_trial_ms` is 0, so `race start` succeeds immediately and the reward (`reward_coins`, line 612-616) is paid again. Repeat as often as you like. `trial_completions` and `trial_best_ms` persist, so the cooldown is the only rate limit.
  - Reach: client reconnect, gateway.rs:1382 to gameplay.rs:1511 to quests.rs:359. The doc comment at 358 says clocks never survive a session, so this may be intended. The cooldown is still the only per-activity rate limit, so the bypass is real unless the design explicitly accepts it.
  - Fix: persist the cooldown deadline as an absolute value in `QuestState` (for example `trial_next_ms`), or keep `next_trial_ms` across `reset_session` and only clear `active_trial`/`last_position`.
