- **[medium] `prototype/osfr-tools/src/restoration/piece_008.rs:1212` - `ChessSession::play` builds the engine bytes before the legality check, and `special_code` indexes the board with unchecked `mv.from`/`mv.to`, so an out-of-range square panics.**
  - **Failure scenario:** a caller passes `ChessMove { from: 64, to: 0, promote: None }` (or `to: 64`). `play` first calls `engine_move_bytes` (1212), which calls `special_code` (1110). That reads `self.squares[mv.from as usize]` at 1070 and panics with index out of bounds. The `apply` call at 1213, which would have returned `IllegalMove`, never runs. The same unchecked index appears at 1112 (`engine_move_bytes`) and at 1099 (`mv.to`).
  - **Reach:** `pub fn play` (1208) takes a `ChessMove` whose `from`/`to` are public `u8` fields. Any future gateway path that decodes a client chess move into `ChessMove` and calls `play` would reach it. Nothing upstream checks `from < 64` or `to < 64`. `is_legal` (1002) would be safe, because it only compares values, so the fix belongs in `play`.
  - **Caveat (why medium, not high):** `piece_008` is not compiled into the crate today. `src/lib.rs` has no `mod restoration`, and only `tests/piece_008.rs` includes it through `#[path]`, so no current client packet reaches this. It becomes a remote crash as soon as the module is wired in.
  - **Fix:** in `play`, before `engine_move_bytes`, add `if mv.from >= 64 || mv.to >= 64 { return Err(ChessError::IllegalMove); }`. Alternatively, run `apply` first and compute the bytes from the pre-move position (clone it first).
