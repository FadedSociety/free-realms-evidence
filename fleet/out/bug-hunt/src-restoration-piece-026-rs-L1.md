**[high] prototype/osfr-tools/src/restoration/piece_026.rs:444-471 (with 636-681 and consume_instance 420-439) - a placement accepts an owned unit that is already placed in another lot, so the same unit can be counted twice and the durable pair can later fail to open.**
- Failure scenario: the pool holds units A and B of definition D at the same tint, both unplaced. The owner has two lots (house1, house2) where they have build permission. (1) `place_fixture(owner, house1, D, A, t)` succeeds. (2) `place_fixture(owner, house2, D, A, t)` also succeeds: `ledger()` stages A once for house1 (placed=1, owned=2), then `housing.place_fixture` stages A again with owned 2 > placed 1, so placed=2. `verify()` passes because `conservation()` sees owned D=2, placed D=2. Both lots now hold the same unit A, and B is still free. (3) Item 081 removes B through `consume_instance(D, B)`. The check at 425-431 only looks for B among placed units, so it passes; the row is removed and `save_stock()` writes the pool with only A. `consume_instance` does not call `verify()`. (4) The next commit fails `verify()` with `PlacedExceedsOwned` (D owned 1, placed 2) and rolls back, so every further commit is refused. On restart, `open()` at 368 calls `verify()` and returns an error, so the furniture state cannot load.
- Reach: client packet 127/1 reaches `Housing::place_fixture` through this transaction's `place_fixture` (444-454). The `item_instance_id` is client-chosen and is checked only for pool membership (housing.rs:444-452, `spawnable`) and a count (housing.rs:462-469). The only identity check in housing.rs:921-928 is per lot, so nothing stops cross-lot reuse. `ledger()` at 671-679 stages every placed unit without de-duplicating by instance. The housing.rs:333-334 comment ("the ledger tracks identity rather than quantity alone") is not what `stage` does: it counts. The module doc at 37-38 says a unit in two lots is refused only at different tints, so same-tint reuse is not intended to be accepted.
- Fix: in `place_fixture`, before calling `housing.place_fixture`, refuse when `self.placed_units()?` already contains `(fixture_definition_id, item_instance_id)` in any lot (return `TransactionError::AmbiguousPlacedTint` or a new "already placed" variant). Also run `self.verify()` in `consume_instance` before `save_stock`, or check conservation on the staged pool before writing.

**[medium] prototype/osfr-tools/src/restoration/piece_026.rs:715-722 - `restore_after_failed_housing_write` returns early when the pool rewrite fails, so the in-memory rollback never runs, contrary to its own doc comment.**
- Failure scenario: a pick-up repaints a unit. `save_stock()` at 504-510 succeeds, then `housing.save_state` at 512 fails. `restore_after_failed_housing_write(.., pool_written=true)` calls `atomic_write(&self.stock_path, ..).map_err(|_| RollbackFailed)?` at 720. If that write also fails, the function returns `RollbackFailed` before `self.restore(house_guid, rollback)` at 722. `self.housing` still has the fixture removed and `self.stock` still has the repainted row, while the disk holds the fixture placed. The caller is told the rollback failed, and any later successful `save_state` writes the memory-only removal to disk.
- Reach: a client packet 127/3 (pick-up) reaches `pickup_fixture` (475-517). The failure needs a filesystem write error on the second write, which is reachable in production (disk full, sharing violation).
- Doc contradiction: the comment at 705-708 says "the in-memory state is rolled back either way". The code does not do that.
- Fix: do the in-memory restore even when the pool write fails, for example `let pool = if pool_written { atomic_write(..).map_err(|_| RollbackFailed) } else { Ok(()) }; self.restore(house_guid, rollback)?; pool?` (restore the memory state first, then report the failed pool write).
