**[medium] prototype/osfr-tools/src/restoration/piece_038.rs:314-325 - `apply` accepts `AddEntry` (and `RemoveEntry`, 326-333) on an `Explorer` collection, storing a per-entry flag that the explorer's completion logic ignores, and reports `Completed` when those flags fill up.**

- **Failure scenario:** Explorer collection 500 lists child collections 501 and 502. Neither child is complete (`is_complete(501)` and `is_complete(502)` are false). Caller runs `apply(1, AddEntry, 500, 501)` then `apply(1, AddEntry, 500, 502)`. The first returns `EntryAdded`, the second returns `Completed` because `all_entries_collected()` on the explorer is true (line 320). The caller is told to act on a completion. Meanwhile `is_complete(500)` is still false (`collection_complete`, 457-470, derives explorer state only from children and never reads the flags), so `resolve_explorer_unlocks` never announces it and `completed_count` does not count it. The two views disagree, and the `Completed` outcome grants what the doc says must come from children.
- **Contradicts its own docs:** `collect` (379-381) and `approach` (353) both refuse explorer entries ("explorer entries never do", line 372; "never collected directly", line 146). `apply` has no such check. `snapshot` (421-422) says explorer entries "have no stored flag ... they always report `false` here", but `apply` writes the flag and `snapshot` (423-431) reports it as `true`. `collected_entry_count` (433-438) counts these fake flags as well.
- **Reach:** `ProfileCollections::apply` (286) is the packet-facing entry point (doc at 284-285 describes it as the handler for each recovered update packet). The only current callers are in `tests/piece_038.rs`, so the module is not yet wired into a network handler. The defect is in the public API regardless. The reconcile step has no kind check before the write, and no caller-side check exists to stop it.
- **Fix:** At the start of the `AddEntry` and `RemoveEntry` arms (or at the top of `apply` after the collection lookup), return `Ok(UpdateOutcome::DuplicateIgnored)` or `Err(ProgressError::...)` when `tracked.kind == CollectionKind::Explorer`, mirroring the check in `collect`. Alternatively, make the `Explorer` branch of `apply` a no-op so that `snapshot` and `completed_count` stay consistent.
