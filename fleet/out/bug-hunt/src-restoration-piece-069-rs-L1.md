# prototype/osfr-tools/src/restoration/piece_069.rs lines 1-546 of 546

Two durability defects in the ledger's write path. Both are reachable only through the ledger's own `append`. The module has no production caller yet (only `tests/piece_069.rs` and `tests/economy_review.rs` call `consider`/`commit`/`recover`), so the reach below is the documented caller contract, not a live packet path. Lower-priority candidates I dropped: the `open` symlink check is TOCTOU-only and not client-driven; `recover` running after `consider` is a doc-ordering note, not a defect.

- **[medium] prototype/osfr-tools/src/restoration/piece_069.rs:479 - the byte bound in `append` checks only the new line plus the record count, not the file's total size, so the document can grow past `MAX_LEDGER_BYTES` (262,144) and then becomes unopenable.**
  - Failure scenario: an account completes about 1,100 distinct quests. Each turn-in writes an intent line of roughly 150 bytes and an applied line of roughly 80 bytes. Every `append` passes the check (`line.len() + records.len()` is far below the cap), so the file reaches about 260 KB and beyond. The next `TurnInLedger::open` sees `metadata.len() > MAX_LEDGER_BYTES` at line 272 and returns "ledger exceeds its byte bound" (line 273), so no turn-in can be considered or recovered for that account.
  - Reach: `consider` (line 377) or `commit` (line 417) or `recover` (line 452) call `append`. The record cap at line 474 is 4,096 records, which is about 500 KB at these sizes, so the byte cap is the one that should bind and does not.
  - Fix: track the byte count of the existing file (for example a `bytes: usize` field set in `open` from `bytes.len()`, incremented in `append`) and check `self.bytes + line.len() + 1 > MAX_LEDGER_BYTES`.

- **[medium] prototype/osfr-tools/src/restoration/piece_069.rs:487-490 - `append` writes and syncs the line to disk before it can fail, but on error it returns without pushing to `self.records`, so a retry appends a duplicate line and the file no longer parses.**
  - Failure scenario: `write_all` succeeds and `sync_data` (line 489) returns an I/O error. The intent line is now on disk, but `consider` returns `Err` at line 377 and `records` does not contain it. The caller retries the same request. `consider` finds no intent in `records` (line 346), `recorded` is unchanged, so the check at line 363 passes and `append` writes a second identical intent line. On the next `open`, `parse_records` hits "duplicate ledger intent" (lines 524-529) and fails permanently, and nothing repairs it because the module refuses to repair. The commit path fails the same way: a failed `Applied` write followed by a retried `commit` writes a second `Applied`, and `parse_records` rejects it at lines 535-539 with "applied record without its intent". A partial `write_all` leaves an unterminated line that makes the next append concatenate into a malformed record.
  - Reach: `consider` (line 377) and `commit` (line 417) and `recover` (line 452) all propagate the `append` error via `?`, so the caller sees `Err` and retries.
  - Fix: on a failed write or sync, either truncate the file back to its pre-append length before returning the error, or push the record into `records` only after `sync_data` succeeds and make `consider`/`commit` consult the file-level state, so a retry never writes a second line for the same key.
