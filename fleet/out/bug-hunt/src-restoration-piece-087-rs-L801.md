**[medium] piece_087.rs:1026-1033 - `confirm(Accepted)` forces the requester online even when the requester has already gone offline, so a logged-out character can show as a ghost-online friend.**
- Failure scenario: A sends B a friend request (`add_request` inserts `(A,B)` into `pending` at line 980). A logs out, and `set_presence(A, false)` sets `accounts[A].online = false` (line 1090). Later B accepts. `confirm(B, A, Accepted)` passes the pending check (line 1011), then sets `accounts[A].online = true` at lines 1029-1033 and builds A's roster row with `online: true` (`build_entry`, line 1269). B now sees A as online, `positions_for(B)` lists A (filter at 1204 passes), and A's roster entry on B's side is online until A's next presence change. The comment at 1027-1028 says the rule holds "because both characters are in the world when the request is answered", but nothing enforces it.
- Reach: the accept is a client packet answered through `confirm` (the `ConfirmStatus` decode is outside this window). Pending entries have no timestamp and no expiry anywhere in the module, so a request can stay pending indefinitely while the requester is offline.
- Fix: only set `online = true` for an account that is currently online (`if account.online` before building the entry), or only set `online` for the responder, who is the one actually answering. Alternatively, build the requester row from its real `online` flag: `build_entry` should use `account.online` instead of the hard-coded `true`.
