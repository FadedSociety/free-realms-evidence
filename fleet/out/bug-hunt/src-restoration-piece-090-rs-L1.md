**[medium] prototype/osfr-tools/src/restoration/piece_090.rs:719-753 - `invite()` never expires or sweeps pending invites, so stale invites fill the per-guild cap of 8 permanently.**
- Failure scenario: an Officer (or the Leader) calls `invite(O, X, t)` for 8 invitee GUIDs that never respond (offline or non-existent characters). Each call returns `Ok`, and each entry is stored in `self.invites`. Afterwards, the cap check at lines 736-743 (`outstanding >= MAX_PENDING_INVITES` where `outstanding` counts every invite with `row.guild == guild_guid`) returns `TooManyPendingInvites` for every real recruit. Nothing removes the 8 entries: `invite()` takes no timeout, and expiry is only checked inside `accept_invite` (lines 774-777), which runs only when that invitee responds. The guild therefore cannot invite anyone until all 8 griefed GUIDs respond.
- Second effect: a re-invite of an invitee whose old invite has already expired hits `contains_key` at lines 732-735 and returns `Ok(())` without refreshing `sent_tick`. The leader is told the invite was sent, but the invitee's accept then returns `InviteExpired`.
- Doc mismatch: the constant comment at line 70 says `MAX_PENDING_INVITES` is "per player", but the code counts per guild (lines 736-739). One of the two is wrong, and the code's per-guild reading is what allows the lockout.
- Reach: `parse_client_request` sub 3 (lines 366-370) takes `player_guid` straight from the packet, and nothing in the module checks that the invitee exists or is online. The rank gate (`role_of`, lines 720-724) lets any Officer trigger this.
- Fix: pass the caller's timeout into `invite()` and drop expired entries for that guild before counting (and before the duplicate check); optionally refresh `sent_tick` when the existing invite is expired. Make the doc match the chosen scope.

**[low] prototype/osfr-tools/src/restoration/piece_090.rs:594-606 and 686-717 - `GuildStore` derives `Deserialize`, so a loaded store skips the `new()` clamp and the `next_guild_id` invariant.**

- Reach: only via a save file, not a remote packet, so this is save corruption. There is no load function in this module; the check would belong at the load boundary.
- Fix: validate on load that `next_guild_id > max(guilds.keys())` and that `max_members` is in `1..=MAX_MEMBERS_LIMIT`, or use a custom `Deserialize` that routes through `new`. In `create_guild`, reject a `guid` already present in `guilds`.
