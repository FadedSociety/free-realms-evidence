One real defect remains.

- **[medium] `prototype/osfr-tools/src/social_chat.rs:743-766` (`similar_text` / `edit_distance`, called from `SpamGate::allow` at 713-717) - every retained line is compared with a full O(n·m) Levenshtein over up to 2048-char messages, so one account can keep the single-threaded gateway loop busy.**
  - **Failure scenario:** One authenticated account sends typed chat (channel Say, for example) of about 2048 distinct letters per message, spaced about 330 ms apart. Each message passes `authorize_free_text` (length ≤ 2048, default permissive filter) and the 330 ms `last_any_ms` gate. Those lines are not similar, so none are rejected as duplicates. Each accepted message is pushed and kept for 30 s, which is about 91 lines. Each new message then runs `edit_distance` against all of them: about 91 × 2048 × 2048 ≈ 3.8·10⁸ cell updates, roughly 0.4–1 s of CPU per accepted message. That is close to continuous CPU use. The gateway receives UDP in one loop (`osfr-gateway.rs:3680`, no thread spawn in `bin/`), so every other player's packets wait behind it. The per-account `ActionBudgets` (5/s, burst 10) does not cut this, because the spam gate already limits accepted messages to about 3/s and the budget charges all of them.
  - **Reach:** Client packet, family 15 sub 1 → `route_typed_chat` (`osfr-gateway.rs:2241-2256`) → `parse_client_chat` (`social_chat.rs:414`, length cap 2048 at 364) → `authorize_free_text` (629) → `spam_gate.allow(...)` (2250) → `SpamGate::allow` (703) → `similar_text` for each retained line (713-717). Nothing upstream limits the cost per comparison; `MAX_SPAM_ENTRIES` (256) and the 30 s retention only bound the number of lines, not the work per pair.
  - **Fix:** In `similar_text`, return false early when the length difference alone already exceeds the threshold (`edit distance ≥ |len(a) − len(b)|`), which cuts the work for mismatched lengths. For the equal-length attack, also bound the comparison, e.g. compare only the first 256 chars of each side in the similarity check, or use a banded edit distance limited to `0.2 × scale`. Either change is small, but it alters the similarity semantics, so the choice should be checked against the `ChatSpeed` notes.
