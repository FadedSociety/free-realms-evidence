**[medium] `prototype/osfr-tools/src/social_lists.rs:447-466` - `logout` notifies only the logging-out character's own friend list, but `login` (430-442) notifies everyone whose list contains that character, so one-sided friendships leave the other side showing a stale "online" status.**
- Failure scenario 1: B and A are both online, A lists B. B calls `remove_friend(A)` (642-661, local-only per the doc comment), so B's list no longer contains A but A's still contains B. B then logs out. `logout(B)` builds `recipients` from `B.friends` (455-460), which no longer contains A, so no 74/3 goes to A and A's list keeps B as online indefinitely.
- Failure scenario 2: A removes B, so only B lists A. B logs in while A is online and sees A online, then A logs out. `logout(A)` builds recipients from `A.friends`, which lacks B, so B is never told and keeps A as online.
- Reach: `osfr-gateway.rs:2160` (RemoveFriend) and `logout`/`disconnect` (`social_lists.rs:929-931`). Remote players can trigger this by removing a friend, which is a normal client action. No upstream check covers it, and the existing tests (`tests/social_lists.rs:155-189`, `tests/friend_positions.rs:331`) only exercise mutual friendships for presence.
- Fix: derive the logout recipients the same way `login` does: `self.profiles.iter().filter(|(_, p)| p.friends.contains_key(&guid)).map(|(g, _)| *g).filter(|g| self.online.contains(g)).collect::<Vec<u64>>()`, and keep the `profile` borrow out of the `online.remove` path.

**[low] `prototype/osfr-tools/src/bin/osfr-gateway.rs:1938` (with `social_lists.rs:571-580`) - `persist_social_changes` writes each changed profile in a separate save, but one friend accept changes two profiles, so a failed second write leaves a one-sided friendship on disk.**
- Failure scenario: A and B accept a friend request. `respond_friend` inserts B into A's list and A into B's list. `persist_social_changes` (2724-2734) saves A's profile, then B's save returns an I/O error (or hits the 1 MiB cap). The `?` at 1938 discards the staged world, so memory keeps the old state, but A's file already records B as a friend. After restart, B does not list A, and the state diverges from what the player was told.
- Reach: `osfr-gateway.rs:2162-2186` (FriendResponse) → `respond_friend` → `persist_social_changes`. The trigger needs a disk failure on the second write, so it is hard to produce remotely; the impact is limited to the atomicity guarantee.
- Fix: write both profiles to a temp location and rename them together, or write the peer's profile first and only then the requester's, and on error revert the written file, so the pair is never left half-saved.
