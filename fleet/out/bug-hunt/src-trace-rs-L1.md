# prototype/osfr-tools/src/trace.rs lines 1-259 of 259

Window reviewed in full (trace.rs 1-259). The bounds checks in `protocol_summary`, `hex_prefix_len`, and `parse_hex` hold up (the wrapper check guarantees `7+size <= len`, and `parse_hex` rejects non-ASCII before slicing). One real defect in the redaction logic:

- **[low] prototype/osfr-tools/src/trace.rs:80-86 - When a 5/6 tunnel header fails validation, `protocol_summary` falls back to treating the whole raw message as the body and never marks it sensitive, so the inner payload (chat, friends, etc.) is shown as hex.**
  - **Failure scenario:** A client sends a reliable payload whose message is `05 00 02 <size u32> <chat body: 0f 00 01 00 ...>`. The flag byte is 2, or `size > len-7`, so the check at line 82 fails. `outer` stays `None` and `body` is the full 7+ byte message. `family` is read from the wrapper (5), so `sensitive_payload(5, _)` is false and `sensitive` stays false (line 79 only checks `top == Some(1)`). `hex_prefix` at line 148 then prints the first 32 bytes, which include the chat body starting at offset 7. The `looks_like_text` heuristic only suppresses ASCII runs of 3+ letters, so UTF-16 text or binary bodies pass through as hex.
  - **Reach:** `osfr-gateway.rs:1313` calls `trace_transport` with `&packet.payload` for every reliable packet the SOE receiver accepts. `trace_transport` (`osfr-gateway.rs:132`) calls `protocol_summary(message)` and then `hex_prefix(summary.body, summary.sensitive || summary.combined ...)` (line 174-177). That trace call happens before the application-level classifier. The classifier (`gateway.rs:606-607`, `tunnel()` at `gateway.rs:247-261`) rejects the same malformed wrapper, because `Reader::bool` refuses values above 1 and the size must match exactly. So the server drops the packet, but the trace has already recorded its inner bytes as "received".
  - **Why it matters:** This breaks the stated invariant at trace.rs:122-124 ("must never show as hex") for an attacker-chosen layout. The exposure is limited to the opt-in local trace file and to the sender's own data, so I rate it low.
  - **Fix:** In `protocol_summary`, fail closed when the header is a 5/6 tunnel but the wrapper is not unwrapped: e.g. `let unwrapped = matches!(top, Some(5|6)) && message.len() >= 7 && message[2] <= 1 && size <= ...; let mut sensitive = top == Some(1) || (matches!(top, Some(5|6)) && !unwrapped);` (structure the check so `unwrapped` is computed first). Optionally align the accepted size and flag rules with `gateway.rs::tunnel` (flag must be 0 or 1, size >= 2, no trailing bytes).

Not reported: `osfr-gateway.rs:1254` omits `|| summary.combined` in the kart-pose trace path, but I could not show a client-reachable combined body there. `Trace::record` can leave a partial JSON line if serialization fails mid-write, but that needs an I/O error and is not client-triggerable.
