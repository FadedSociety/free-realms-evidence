# prototype/osfr-tools/src/trade.rs lines 1-800 of 1624

Window `trade.rs` 1-800 (with the helpers it calls, 960-1300 and 1455-1624, and `maintain`/`timeout`/`handle` for context). Most of the window is sound: client ids are checked against the server's pending/session maps, `offer_item` and `offer_coins` re-validate against the server's snapshot, `open_session` blocks everything during `Settling`, `close_active` refuses to end a settling session, and the packet builders' `?` paths cannot fail after validation (`validate_trade_inventory` and `validate_state` bound count, consumed and stored values, and `update_item_count_packet` only sees ids that were just found in the inventory). I found no panic, unbounded growth, or client-trusted item/coin/quantity in the window. The findings below are the two defects I could show.

**[medium] `osfr-gateway.rs:2697-2706` (outside my window, root cause for the trade.rs settlement contract) - a commit error drops the settlement without calling `TradeService::settled`, so both sessions wedge until restart.**
- Failure scenario: a settlement is queued by `accept` (`trade.rs:666-671`). `settle_trades` takes the whole queue with `mem::take` (line 2697). `commit_trade` then returns `Err` from any `?` in `commit_trade_parties` (lines 2617-2638: journal `File::create`/`rename`, `save`, `remove_file`, or `serde`). The `?` at line 2698 aborts the function. The settlement is already removed from the queue, so `settled(session_id, _)` is never called, and any later queued settlements in the same batch are dropped too. `trade.rs:690-693` keeps `settlement: Some(..)`. From then on `open_session` returns `Settling` (`trade.rs:985-986`), `cancel` returns `Settling` (`trade.rs:714-715`), `close_active` is a no-op (`trade.rs:1059-1065`), so `disconnect` (`trade.rs:756-765`) and `maintain` (`trade.rs:859-865`) cannot end it. `unregister_player` keeps the entry because the guid is still busy (`trade.rs:771-773`). `register_player` then returns `PlayerBusy` for that guid (`trade.rs:267-268`), and `invite` refuses it (`trade.rs:344-349`). Both players stay busy until the process restarts.
- Reach: `route_application` / `route_trade` queues the settlement (`osfr-gateway.rs:2105`). It is committed in `settle_trades` (called at line 2008), where the `?` at 2008 propagates the error out of the session's message handling. A remote player cannot pick the I/O error directly, so this is a server-fault trigger (disk full, permission error, a failing `save`).
- Caveat on the fix: simply calling `settled(id, false)` on error is not clean either. A `save` may already have landed for one side, and the journal remains for recovery at restart (lines 2653-2687). Reporting "cancelled" while the disk may be partly written needs a decision. The minimum fix is to stop the `?` from aborting the loop and to answer every taken settlement: match on `commit_trade`, log the error, treat it as not committed, and call `settled(session_id, false)` so the sessions unwedge.

**[low] `trade.rs:403-452` - `reply_invite` accepts an invite past `invite_ttl_ms`; expiry is only enforced by `maintain`.**
- Failure scenario: an invite is opened at t=0. The invitee replies accept (sub 3) at t=60.2 s, before any `maintain` call has run since t=60.0 s. `reply_invite` never compares `now_ms` with `invite.opened_ms + invite_ttl_ms`. It opens the session (`trade.rs:436-450`) even though the rules say the invite "lives" 60 s (`trade.rs:129-130`).
- Reach: the sub-3 route is `route_trade` → `handle` → `reply_invite` (`osfr-gateway.rs:2095-2107`). `maintain` runs only after the message batch (`osfr-gateway.rs:1911`), so the window is up to one tick. The impact is small.
- Fix: at the top of the accept path, `if now_ms.saturating_sub(invite.opened_ms) >= self.rules.invite_ttl_ms { return Ok(self.close_pending(session_id, invite)); }`.
