# prototype/osfr-tools/tests/medic_entry_chain.rs lines 1-892 of 892

Reviewed `prototype/osfr-tools/tests/medic_entry_chain.rs` lines 1-892 (plus the helpers it calls in `support/npc_quest_chain.rs` and `support/medic_entry.rs`). Most assertions are real: the exact state comparisons in `assert_no_offer` / `assert_packet_changes_nothing`, the `QuestStatus` and coin/XP deltas, and the save-envelope round trip in `relog_preserves_completed_history` all test production behaviour. The findings below are the weak spots.

- **[medium] tests/medic_entry_chain.rs:98-105 `offer_checked` - it asserts that the 49/1 intro locale id is `0`, so the intro text is never verified and the test pins a placeholder.**
  - Why it cannot catch a regression: the expected value is the documented "lead gap" sentinel, not the recovered client id. A server that sends the correct intro id would fail this check, while one that sends the wrong non-zero id is also caught only as "not 0". Nothing checks that the intro is the quest's real line, and the check is applied to every offer in the chapter (lines 140, 170, 208, 437, 510, 709, 344).
  - Fix: either assert the recovered intro ids per quest (for example `PILL_INTRO_TEXT`/`LEVEL_INTRO_TEXT` style constants, with the EXAM/HOUSE/VITAMINS values once recovered), or make the helper record the gap explicitly (`#[ignore = "..."]` on a dedicated test) rather than asserting 0 inside every chapter test.

- **[low] tests/medic_entry_chain.rs:225, 454, 525 `release_end_screen(..., VITAMINS, GREYLI, 0, ...)` - the Vitamins end-screen text is pinned to 0, so the 3090005 debrief is never checked.**
  - Why it cannot catch a regression: `release_end_screen` (support/npc_quest_chain.rs:498-507) compares bytes 18..22 with the passed value, so any server change that emits a different non-zero end text, or drops the text in a way that still yields 0, passes. The relog test at 798-808 does not re-check the end text for VITAMINS either.
  - Fix: track the 3090005 end-text gap as an explicit `#[ignore]`d/known-gap assertion, or add a canary that fails once a real completion-line id is recovered (for example a constant in `support/medic_entry.rs` that the test must consume once the gap is closed).

- **[low] tests/medic_entry_chain.rs:850-887 `two_medics_progress_independently` - the name claims independent progression, but the body never checks that one ledger is unaffected by the other before the second character acts.**
  - Why it cannot catch a regression: the loop at 862-872 runs talk, end screen and turn-in per character, and the final checks (lines 873-886) only compare each game's own totals. Nothing asserts that `first`'s counts or pending turn-in stay at their pre-talk values while `second` is in progress, or that `second`'s state is unchanged by `first`'s talk. A shared-ledger bug that let `first`'s Talk touch `second` would only be caught indirectly, through the later `talked.changed` assertion.
  - Fix: before the loop, assert `counts(&second, EXAM) == vec![0]` and `pending_turnin(&second) == None` after `first`'s talk; and after each character's finish, compare the other game's `saved(...)` bytes to a snapshot taken before the step.
