The findings below are the weak spots.

- **[medium] tests/piece_075.rs:190 `route_membership_order_and_timer_stay_reported_gaps` - the only check beyond the gap flags is `validate().is_ok()`, which cannot catch a model-table regression.**
  - Why it cannot catch a regression: `mailbox_row` (src 122-125) and `validate` (src 687-698) both derive `model_id`/`model_file` from `kind` with the same match. Every row is built through `mailbox_row`, so the `ModelMismatch` arm can never fire for shipped data. A change to the model mapping in `mailbox_row` alone (for example, giving `PostboxGroup` model 910) would leave `validate()` returning Ok. The test name also says nothing about validation.
  - Fix: assert the recovered model per kind directly, for example `assert_eq!(mailbox(2297).unwrap().model_id, 340)` for a `PostboxGroup` and the same for a `StreetMailbox` at 910. Also add a value check that `validate()` is not vacuous, such as a test that feeds it a duplicate row or an empty-text row and expects the matching `RouteError`. Or move the `validate()` call into its own test with that name.

- **[medium] tests/piece_075.rs:162-176 `delivery_run_validates_targets_and_completion_without_inventing_a_route` - `DeliveryRun::progress()` and the `DeliveryProgress` value returned by `deliver()` are never inspected.**
  - Why it cannot catch a regression: `deliver(...)` is only checked with `.is_ok()` at lines 162, 173 and 174. `progress()` is never called, and `remaining()` is checked only after the first delivery. Changing `progress()` to report `delivered` as `targets.len()` or `total` as `delivered.len()` passes. Also, after the rejected duplicate and unknown deliveries (lines 164-171), `remaining()` and `progress().delivered` are never re-checked, so a bug that counts a rejected call as progress would pass.
  - Fix: assert `run.deliver(1755)` returns `Ok(DeliveryProgress { delivered: 1, total: 3 })`, assert `run.progress()` after each step, and assert `run.remaining() == 2` and `run.progress().delivered == 1` again after the duplicate and unknown rejections.

- **[low] tests/piece_075.rs:149-152 `delivery_notification_matches_the_client_lua` - the name says the test checks the client Lua, but it only compares the Rust constants with literals typed in the test.**
  - Why it cannot catch a regression: the Lua is never read. The test would still pass if `ScriptsBase.lua` changed the string id or icon, and it would fail only if someone edited the constant in `src` without also editing the literal in the test. The values do match the shipped Lua today (ScriptsBase.lua:11639-11640), so the test is correct now but does not verify the claim its name makes.
  - Fix: either rename it to `delivery_notification_constants_are_pinned` and say the Lua was checked by hand, or add a source-equality check that reads the recovered Lua file (or the checker's output) and asserts it contains `CompleteObjective(Ui.GetString(388255)` and `iconSlideHorizontal", 1, 1237`.

- **[low] tests/piece_075.rs:184-191 `route_membership_order_and_timer_stay_reported_gaps` - the gap flags are pinned as literals, so they only catch a flip, not a missing recovery.**
  - Why it cannot catch a regression: these are constant-vs-literal assertions (`assert!(!ROUTE_ORDER_RECOVERED)`). They fail only when someone flips a flag, and a new route-order table that is added without flipping the flag would pass. This is the intended gap pin, so it is a weak check of "not recovered", not a bug.
  - Fix: keep the pins, and add a cross-check that the flags agree with the data, for example `assert!(ROUTE_MEMBERSHIP_RECOVERED == false || ...)`, or tie `DELIVERY_TIMER_SECONDS` to a value check. At minimum, document that these are deliberate sentinels so a reviewer knows the test does not check the evidence.
