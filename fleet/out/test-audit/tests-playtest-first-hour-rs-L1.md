Window reviewed: `prototype/osfr-tools/tests/playtest_first_hour.rs` lines 1-1097 (read in full). Most assertions are real: they compare live state (`game.state()`, `saved()` bytes, `counts`, `coins`, `profile_xp`, `pending_turnin`) against values set before the step, and the kill/quest checks go through the production handlers. The findings below are the exceptions.

- **[medium] tests/playtest_first_hour.rs:906-915 the_first_hour_loop_uses_no_dev_commands_and_leaves_the_character_free - the "no chat/dev command" check runs `assert_not_chat` on packets the test itself built with the quest/NPC/job builders and never sent to the game.**
  - Why it cannot catch a regression: `npc_interact`, `npc_select`, `dialogue_choice`, `quest_reply`, `quest_end_reply` and `select_job` return fixed family-26/49/45/39 shapes. The check only tests their first two bytes against `[15, 0]`, which a builder cannot produce by its design. Nothing in the loop sends a 15/x packet through `handle_in_world`, so a change that sent a `realm` chat request during the loop would not reach this assertion. The `may_run` checks at 892-905 read the session's dev flags, not the loop's traffic. The only live chat check is on the kill and turn-in replies at 918-934, which does not cover inbound requests.
  - Fix: pass each step's real request (npc_interact, dialogue choice, quest reply, job select, end reply) through `game.handle_in_world` and assert that the outcome has no `[15, 0]` reply and no state change beyond the quest step. Alternatively, make `send` record every inbound packet and assert that none starts with `[15, 0]`.

- **[low] tests/playtest_first_hour.rs:1093-1096 a_new_character_accepts... (test name: the negative-definition check is in `the_loop_uses_only_server_owned_ids_and_authoritative_hits`) - "refused by the production content loader" is checked only by `error.kind() == InvalidData`.**
  - Why it cannot catch a regression: any `InvalidData` from `Gameplay::load` passes, including a broken fixture JSON or an unrelated validator. The refusal is the `validate_actor` guard at `src/encounter.rs:2749` (`definition_id < 0`), but the test never checks that the same file with definition 0 loads. A change that makes the loader refuse every field-enemy file would still pass.
  - Fix: first assert `Gameplay::load(fixture.path(), None)` succeeds with `wolf_content_with_definition(0)`, so the refusal is shown to come from the definition. Then assert the error message names the actor or the definition, not just the kind.

- **[low] tests/playtest_first_hour.rs:946-958 the_first_hour_loop_uses_no_dev_commands_and_leaves_the_character_free - "the character is in a valid place" is checked on the test's own `at` value after a save round-trip.**
  - Why it cannot catch a regression: `envelope.character == at` compares the value the test just wrote with itself, and `supports_location` runs on that same fixture position. The comment at 944-946 says gameplay does not move the position in this harness, so no gameplay change can affect the check. The test name's "leaves the character free" is not tested by this step.
  - Fix: take the position from the session (or the gateway's commit output) rather than from `at`, and assert it is unchanged across the whole loop. Otherwise, drop the claim from the name and the comment.
