Two findings:

- **[medium] prototype/osfr-tools/tests/support/npc_quest_chain.rs:412-421 `talk_step` - the helper claims to complete an ordered Talk objective and its message says "did not advance its objective", but it only asserts `talked.changed`.**
  - Why it cannot catch a regression: any state mutation that sets `changed` (for example a position or dialogue-state write, or an unrelated reward) still passes, even when the objective counter never moves or no 49/8 or 49/9 packet is sent. `changed` is a generic flag (`src/gameplay/npc.rs` sets it in many unrelated paths), so it does not prove objective progress.
  - Fix: assert the objective outcome itself, e.g. `assert!(objective_update(&talked, quest, objective, expected_count) || objective_complete(&talked, quest, objective) || objective_activated(&talked, quest, objective), ...)` or compare `counts(game, quest)` before and after. Those helpers already exist in this file (lines 801-827). Alternatively, rename the function and message to match what is actually checked.

- **[low] prototype/osfr-tools/tests/support/npc_quest_chain.rs:218-238 `fill_bag` - the doc says it fills "exactly BAG_SLOTS stacks" so "the next new stack is refused", but when existing items already number at least `BAG_SLOTS` the range is empty and nothing is added, and the helper never checks the final count.**
  - Why it cannot catch a regression: a caller whose fixture already holds 100+ items gets an unfilled-or-overfilled bag with no panic; a test that depends on the refusal would then rely on the wrong precondition and could pass for the wrong reason, or fail for an unrelated reason.
  - Fix: add `assert_eq!(state.inventory.items.len(), BAG_SLOTS, "fill_bag must leave exactly BAG_SLOTS stacks")` after the loop, so an over-full starting bag fails loudly instead of silently breaking the premise.
