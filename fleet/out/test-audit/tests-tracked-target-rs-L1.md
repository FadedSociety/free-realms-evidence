# prototype/osfr-tools/tests/tracked_target.rs lines 1-217 of 217

Window: `prototype/osfr-tools/tests/tracked_target.rs` lines 1-217. Read against `src/quest_journal.rs` (`Pin::encode` 251-268, `locate` 283-308, `tracked_pin` 313-324, `Tracker` 330-342). The layout, clear, per-kind location, zone, and tracker-change tests are sound and would catch the mutations I checked. Three findings:

- **[medium] tests/tracked_target.rs:210 a_new_session_sends_the_pin_again - the name claims a session/reconnect behaviour, but the body only builds a fresh `Tracker::default()` and asserts `is_some()`, which is the same first-update case already covered at line 197.**
  - Why it cannot catch a regression: nothing about a session, save, or reload is exercised. `Tracker` derives only `Clone, Debug, Default` (quest_journal.rs:330), so there is no persistence path to break. Any change to how the pin is stored or restored on login (for example the player record keeping `sent` and reloading it) leaves this test green, because it never touches that path. The test would still pass if the pin were restored as already shown, as long as a fresh tracker sends once.
  - Fix: either rename it to something like `a_fresh_tracker_sends_its_first_pin` and drop the session wording, or exercise the real reconnect path: serialise or hand the tracker's state to the login/zone-reload code and assert that the pin is re-sent (or deliberately not re-sent) for the new session.

- **[medium] tests/tracked_target.rs:154-175 only_the_selected_quests_open_objectives_are_tracked - the comment promises "forged, another player's, not active, finished" selections give nothing, but `tracked_pin` (quest_journal.rs:313-324) never checks status or ownership; it only checks `selected?` and the list it is handed.**
  - Why it cannot catch a regression: the test only passes `None` or an empty slice, and objectives that are already known to be open. If `tracked_pin` (or its caller) stamped the selected quest id onto objectives from a different quest, or accepted a finished/inactive quest's objectives, every assertion here still passes. The "open" part of the name is supplied by the test's own input, not by the code.
  - Fix: add a case where `selected` names quest A but the objectives belong to another quest, and a case where the caller's open list is empty for a completed quest id, and assert `None` for each; or narrow the name and comment to what is really checked (first located open objective, empty list, no selection).

- **[low] tests/tracked_target.rs:141 a_position_that_is_not_finite_is_never_sent - the name says the pin is "never sent", but the body only checks `locate` returns `None`; no `Tracker::update` or `Pin::encode` call is made.**
  - Why it cannot catch a regression: a change that let a non-finite position reach the tracker through another route (for example a direct `Pin` built from content, or `Tracker::update(Some(pin))` with NaN) would pass, since the test never goes through `update`. The test also covers only the `VisitPosition` branch, although the finite check at quest_journal.rs:301 is shared by all branches.
  - Fix: after the `locate` check, assert that `Tracker::default().update(Some(nan_pin))` is either `None` or that the path is blocked upstream, and add one NPC or POI case with a NaN coordinate so the shared guard is pinned from more than one branch.
