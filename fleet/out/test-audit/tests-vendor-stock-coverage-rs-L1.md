- **[medium] tests/vendor_stock_coverage.rs:793 `no_vendor_stock_row_uses_a_fuzzy_or_family_substitute` - the name claims a check over every vendor stock row, but the body only inspects the 22 rows in `ADDED_STOCK` (loop at 815).**
  - Why it cannot catch a regression: any other row in `vendors.json` (for example, an existing row rewritten to a gender or family sibling, or one with a fuzzy `source_stock_name` mismatch) is never examined, so the test still passes. Even within the 22 rows, the only source-tag check is `source_tags[0] == "client"` (line 841), so the rest of the tags are unchecked.
  - Fix: either rename the test to something like `added_stock_rows_are_exact_catalogue_matches`, or iterate over every `vendors.json` item and assert the same invariants: `item_source.mapping_policy` contains the exact-name policy, `source_stock_name` equals the locale name it maps to, and any `variant_sibling_item_ids` is reciprocal with equal `source_stock_name`. Add a canary for an arbitrary non-ADDED row whose `variant_sibling_item_ids` is non-empty but not reciprocal.

- **[medium] tests/vendor_stock_coverage.rs:553 `assert_exception` (called from the selected-hub test at 463 and 499) - the "evidence-backed exception" check is only a check on the test's own constants.**
  - Why it cannot catch a regression: `source` and `reason` come from the hard-coded `StockException` table (lines 156-190, `unresolved()` / `unresolved_named()` helpers, and the literal at 158-162). `assert_exception` only checks that they are non-empty and that `source` starts with `data/content/`. The `reason` string is never compared to the content file, and the null-price claim in the literal at 161 ("(R) Bait (57012) has a null stores.json purchase price") is never verified against `stores.json`. If Bait (57012) gains a purchase price, the resolved record will still count as an exception as long as its `items` contain a NoSale row, and the test still passes.
  - Fix: for the resolved exception, assert that `prices()` has no entry with a positive price for item 57012 (or that `stores.json` row 57012 has `purchase_price_coins` null), and for the unresolved exceptions assert that the `reason` text in `vendors_unresolved.json` is non-empty and matches the table's `unresolved`/`unresolved_named` classification. Alternatively, drop the `reason` field, since it currently documents nothing that is checked.
